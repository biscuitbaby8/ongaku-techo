# Google AdSense 審査 調査結果と改善プラン

調査日: 2026-07-26 / 対象: https://ongakutecho.com （本番デプロイ 2026-07-17 時点のコード）

このドキュメントは「なぜ何度も審査に落ちているのか」を実際のコードと本番HTMLから調査した結果と、
通過に向けた改善プランをまとめたものです。
末尾の「未確認事項」も併せてご確認ください。

---

## 結論（先に要点だけ）

落ちている原因は大きく2つで、性質がまったく違います。

1. **クローキング（Googleスパムポリシー違反）を実装してしまっていた** → 今回のコミットで撤去済み
   これは「何度申請しても落ちる」タイプの原因です。
2. **1ページあたりの独自テキストが平均46文字の空ページが1,004枚ある** → コンテンツ作業が必要（Phase 2）
   これはコードでは解決できず、原稿を書く／ページ構成を変える必要があります。

その他に、重複ドメイン公開・sitemapの404・プライバシーポリシーの記載漏れといった
「減点材料」が複数ありました。コードで直せるものは今回まとめて修正しています。

---

## 調査結果

### 1. 【最重要・修正済み】クローラーにだけ見せて利用者から隠すコード（クローキング）

`scripts/generate-static-pages.js` の `generateHomepage()` が、トップページの `<div id="root">` の
**手前**に用語一覧ブロック（`#seo-content`）を挿入し、Reactのマウントを検知して
そのブロックを DOM から削除する MutationObserver を仕込んでいました。

元のコードのコメントにも意図が書かれていました:

```
// Googlebot renders JS but takes a "screenshot" of the initial visible content
// Unlike CSS display:none, DOM removal happens AFTER Googlebot captures content
```

**確認したこと**

- 本番 `https://ongakutecho.com/` の HTML に、当該ブロックと削除スクリプトが実在（Vercel API経由で取得）
- ヘッドレスブラウザで開くと、Reactマウント後に `#seo-content` が DOM から消えることを再現

これは「検索エンジンに見せる内容と利用者に見せる内容を意図的に違えている」= クローキングそのもので、
Google のスパムポリシー違反です。AdSense はスパムポリシー違反サイトを承認しないため、
コンテンツをどれだけ足しても、これが残っている限り通らない可能性があります。

**修正内容**: 削除スクリプトを廃止し、静的ブロックを `#root` の**あと**に移動しました。
利用者もページ下部までスクロールすれば同じものを読めるため、隠していることになりません。
SEO上のクロール可能なテキストも維持されます（`<h1>` の重複も解消）。

---

### 2. 【最重要・要対応】コンテンツが薄すぎる（低品質コンテンツ / 大量生成ページ）

`src/data/termsData.js` を集計した実測値です。

| 指標 | 実測値 |
|---|---|
| 用語ページ数 | 1,004ページ |
| 辞典の独自テキスト総量 | 46,412文字 |
| **1ページあたりの平均独自テキスト** | **約46文字** |
| `detail` が30文字未満 | 258件（26%） |
| `detail` が45文字未満 | 601件（60%） |
| 同じ `meaning` を共有する用語 | 35グループ・75件 |

本番の1ページ（`/term/pianississimo/`）の中身を実際に確認すると、固有のテキストは

- 見出し: `Pianississimo` / 読み: `ピアニッシッシモ`
- 意味: `できるだけ弱く`（7文字）
- 解説: 57文字

の**合計約70文字**だけで、残りはヘッダー・関連用語8件のリンク・フッターという全ページ共通の定型部分です。
本文比率はおおむね5〜10%程度です。

さらに、`detail` が実質的に相互参照だけの項目が48件ありました（例:「Diminuendoのドイツ語。」「Attaccaの別表記。」「Graziosoに近い。」など）。

Google から見ると、これは
「テンプレートにデータを流し込んで大量生成した、単独では価値のないページ群」
= AdSense の不承認理由で最も多い**「価値の低いコンテンツ」**に該当します。
用語数の多さは、この文脈では加点ではなく減点方向に働きます。

**今回コードで直したのはデータ不整合のみです（下記）。本質的な対策は Phase 2 を参照してください。**

- 完全重複エントリ: `Coda-sign`(id:330) と `Coda sign`(id:454) が同じURL `/term/coda-sign/` を生成し、
  片方が静的生成時に**上書きされて消えていた** → 重複を削除し、残す方の解説を加筆して統合
- 解説文の完全コピペ: `Caloroso` と `Con calore` の `detail` が一字一句同一 → `Con calore` を書き直し
- 今後同じことが起きないよう、スラッグ重複を検知したらビルドを失敗させるチェックを追加

### 3. 【修正済み（一部要操作）】同一サイトが7つ以上のドメインで公開されている

Vercel に、同じリポジトリの本番デプロイが**3プロジェクト**存在していました。

| プロジェクト | 公開URL | 状態 |
|---|---|---|
| `ongaku-techo` | ongakutecho.com / www / ongaku-techo.vercel.app 他 | 本番 |
| `ongaku-techo-m8lz` | ongaku-techo-m8lz.vercel.app | READY・公開中 |
| `ongaku-techo-wm8h` | ongaku-techo-wm8h.vercel.app | READY・公開中 |

`ongaku-techo-m8lz.vercel.app` を実際に取得したところ、本番と同一内容を HTTP 200 で返しました。
つまり**同じ1,004ページが複数ドメインに存在**しており、重複コンテンツの塊になっています。
どのコピーも `robots.txt` は全許可で、Google が本番ドメインではなく複製の方を評価してしまう可能性もあります。

**修正内容**: `vercel.json` に、ホストが `*.vercel.app` の場合だけ
`X-Robots-Tag: noindex, nofollow` を返すヘッダーを追加しました（本番ドメインには影響しません）。

**要操作**: 使っていない `ongaku-techo-m8lz` と `ongaku-techo-wm8h` は Vercel のダッシュボードから
**プロジェクトごと削除**してください。noindex は応急処置で、根本対応は削除です。

### 4. 【修正済み】sitemap.xml が404になるURLを申告していた

`scripts/generate-sitemap.js` がカテゴリ一覧に「お気に入り」を含めていたため、
`/index/お気に入り/` を sitemap に出力していました。
このURLは静的ページを生成していないため、実際にアクセスすると **404** を返します（本番で確認済み）。

加えて、このスクリプトはビルドに組み込まれておらず、`public/sitemap.xml` は
`lastmod` が2026年3月のまま手動更新に依存していました。

**修正内容**: 「お気に入り」を除外、`about.html` / `contact.html` を追加、
`npm run build` の先頭で sitemap を自動生成するようにしました（1,016 → 1,014 URL、`lastmod` も自動更新）。

### 5. 【修正済み】プライバシーポリシーが実態と合っていない

AdSense の審査ではプライバシーポリシーの内容も確認されます。以下の不整合がありました。

| 問題 | 内容 |
|---|---|
| 使っていないツールを記載 | 「Googleアナリティクスを利用しています」と書かれているが、GAは導入されていない |
| 使っているツールの記載なし | 実際に使っているのは Vercel Analytics / Speed Insights（`src/main.jsx`） |
| **第三者への送信を開示していない** | AIスマートスキャンで**撮影画像がGoogleのGemini APIに送信される**ことが未記載 |
| クラウド保存の記載なし | ログイン機能で**メールアドレスと学習データがSupabaseに保存される**ことが未記載 |
| LocalStorage の説明が不正確 | 「サーバーへ送信されることはありません」と断言しているが、ログイン時は同期される |

**修正内容**: 上記5点を反映しました（Gemini API への画像送信、Supabase でのアカウント・学習データ保管、
Vercel Analytics、GA記載の削除、LocalStorage 説明の条件付け）。
法務的な文面としてご自身でも一度目を通してください。

### 6. 【要対応】EEA/UK 向けの同意管理（CMP）がない

現在の Cookie バナーは「同意する」ボタンのみで、拒否する手段がありません。
また Google 認定 CMP でもありません。

Google は2024年1月以降、AdSense を利用するサイトが EEA（欧州経済領域）および英国のユーザーに
広告を配信する場合、**Google認定CMPの利用を必須**としています。
日本向けサイトでも、これらの地域からのアクセスがある限り対象になります。

**対応方法（Phase 3）**: AdSense 管理画面の「プライバシーとメッセージング」から
**GDPRメッセージを作成**するのが最も簡単です（Google製・無料・認定済み）。
現在の自作バナーは、日本向けの LocalStorage 説明として残しつつ、拒否ボタンを追加するのが望ましいです。

## 改善プラン

### Phase 1 — 再申請の前提条件（今回のコミットでほぼ完了）

| # | 項目 | 状態 |
|---|---|---|
| 1 | クローキング（`#seo-content` の削除スクリプト）の撤去 | ✅ 完了 |
| 2 | sitemap の404URL除去・ビルドへの組み込み | ✅ 完了 |
| 3 | 重複ページ・コピペ解説の解消＋再発防止チェック | ✅ 完了 |
| 4 | プライバシーポリシーを実態に合わせる | ✅ 完了 |
| 5 | `*.vercel.app` を noindex | ✅ 完了 |
| 6 | 拡大可能な viewport | ✅ 完了 |
| 7 | **不要な Vercel プロジェクト2件（m8lz / wm8h）を削除** | ⚠️ 要操作 |
| 8 | **Search Console で sitemap を再送信し、主要ページのインデックス登録をリクエスト** | ⚠️ 要操作 |

### Phase 2 — 本命。コンテンツの作り直し（これが最優先課題）

Phase 1 だけでは、2. の「平均46文字のページが1,004枚」という状態は変わりません。
ここが解決しないと、また同じ理由で落ちる可能性が高いです。選択肢は2つです。

#### 案A: 1,004ページすべてを厚くする
1ページ400〜800字に加筆すると、合計40〜80万字の執筆が必要です。現実的ではありません。**非推奨。**

#### 案B: ページ数を絞って厚くする（推奨）

「1,000枚の薄いページ」を「200枚の読み応えのあるページ」に組み替えます。

1. **よく使う用語 150〜200語だけを独立ページにする**（1ページ600〜1,000字）
   1項目あたりの構成テンプレート例:
   - 読み方・語源（どの言語のどんな単語から来たか）
   - 楽譜でこの指示を見たとき、何を求められているのか
   - 実際の演奏のコツ（ピアノ／弦／管など楽器別に一言ずつ）
   - 混同しやすい用語との違い（例: Adagio と Andante、rit. と rall.）
   - この指示が印象的に使われる有名曲の例
2. **残り約850語は個別ページを作らず、カテゴリ一覧ページ内の項目に格下げする**
   - `isFeatured: true` のような1フラグを `termsData.js` に持たせ、
     `generate-static-pages.js` でそのフラグがある用語だけ個別ページを生成すれば実装できます
   - 既存URLを消す場合は、カテゴリ一覧ページへ301リダイレクト（`vercel.json` の `redirects`）
3. **カテゴリ一覧ページ（強弱／速度／奏法／表情／構成）を「読み物」にする**
   単なるリンク集ではなく、そのカテゴリの全体像を解説する導入文2,000字程度を各ページに追加します
4. **辞書以外のオリジナル記事を5〜10本追加する**
   「独自の付加価値」を審査側に説明できる材料になります。例:
   - 初心者がつまずく強弱記号の読み方
   - メトロノーム練習の正しい使い方
   - Andante と Adagio は何が違うのか
   - チューナーのセント表示の読み方
   - 楽譜の速度指示を「BPM」に読み替える早見表

#### 案B'（時間対効果が最も良い進め方）

いきなり200語やるのは大変なので、**まず50語を厚くして記事3本を足し、その状態で再申請**。
通ればそのまま残りを進める、という段階的アプローチをおすすめします。

### Phase 3 — 承認後、または並行して

| 項目 | 理由 |
|---|---|
| Google認定CMP（AdSenseのGDPRメッセージ）を導入、Cookieバナーに拒否ボタン追加 | ポリシー要件（6.） |
| Gemini API キーを Vercel の Serverless Function（例 `/api/scan`）に移す | キー露出の解消。クライアントからキーが消える |
| Tailwind を CDN からビルド時生成に変更 | 表示速度・Core Web Vitals |
| `termsData.js` を分割し、初回読み込みを軽くする | 同上（現状610KB） |
| `AdSlot` の `SHOW_ADS` を `true` にする／自動広告を設定 | 承認後の広告表示 |

## 再申請の手順（おすすめ）

1. Phase 1 の要操作2件（Vercelプロジェクト削除・Search Console）を済ませてデプロイ
2. Search Console の「URL検査」でトップ・一覧・主要な用語ページのインデックス登録をリクエスト
3. Phase 2 の最低ライン（案B': 50語の加筆＋記事3本）を投入
4. **2週間ほど間隔をあけてから再申請**
   修正直後の再申請は、Googleのクロールが追いついておらず同じ結果になりやすいです

## 未確認事項・お願い

- **AdSense からの不承認メールの文面を共有いただけると、原因をさらに絞り込めます。**
  「価値の低いコンテンツ」「ポリシー違反」「サイトの停止状態または利用不可」など、
  記載されている理由によって優先順位が変わります。
- この調査環境からは `ongakutecho.com` へ直接HTTPアクセスできない（ネットワークポリシーによる制限）ため、
  本番HTMLの確認は Vercel API 経由で行いました。ブラウザでの見た目の最終確認はお願いします。
- プライバシーポリシーの追記部分は、法務的な観点でご自身でも内容をご確認ください。
